BUSINESS LOGIC VERIFICATION
================================================================================

Scenario 1: Happy Path (Request → Accept)
  ✅ User A sends request to User B → 201 Created
  ✅ User B sees pending request → GET /pending
  ✅ User B accepts → 200 OK
  ✅ Users appear in friend lists → GET /friends
  ✅ Duplicate request → 409 Conflict (users already friends)

Scenario 2: Self-Request Prevention
  ✅ User A sends request to themselves → 400 Bad Request
  ✅ Error message: "Cannot send friend request to yourself"

Scenario 3: Rejection and Re-request
  ✅ User A sends request → 201 Created
  ✅ User B rejects → 200 OK
  ✅ User A re-sends request → 201 Created (reuses record, clears respondedAt)

Scenario 4: Authorization Enforcement
  ✅ User B tries to accept as User C → 403 Forbidden
  ✅ User C tries to remove friendship between A & B → 403 Forbidden

Scenario 5: Friendship Status Query
  ✅ No relationship → { isFriend: false, status: 'none' }
  ✅ Pending request → { isFriend: false, status: 'pending' }
  ✅ Accepted → { isFriend: true, status: 'accepted' }

================================================================================
NON-BLOCKING CONSIDERATIONS
================================================================================

⚠️ WARNING (Low Severity - Documentation Only):

1. Race Condition in Simultaneous Requests
   - If User A and User B request each other simultaneously, two records created
   - PostgreSQL transaction isolation makes this low probability
   - Mitigation: Database-level unique constraint on (requesterId, addresseeId) pairs
   - Impact: Low (manageable, edge case)

2. Bidirectional Request Conflicts UX
   - If mutual requests happen simultaneously, both show as pending
   - Not a bug, just a UX consideration to document
   - Impact: Low (rare scenario, acceptable behavior)

Both are acceptable for production. Consider these in future optimization passes.
